# NewSqadBot v1.9.0 — Reliability & Operations

Тип релиза: инфраструктурный. Новых миграций SQLite нет; прежние роли, заявки, тикеты и баланс остаются.

## Реализовано

### Операционная диагностика

- `app/core/observability.py` сохраняет ограниченный журнал служебных событий в `DATA_DIR/operations.json`: подключение, обрыв и восстановление Gateway, перезапуск воркеров, загрузочные ошибки модулей и агрегированные ошибки Discord HTTP.
- Журнал не содержит текстов сообщений, Discord-токенов, каналов, имён и идентификаторов пользователей. Максимальная история — 40 событий.
- Счётчики HTTP учитывают **исключения, вышедшие из discord.py**. Библиотека может обработать HTTP 429 самостоятельно, поэтому значение не является полным счётчиком всех внутренних задержек и повторов.
- Веб-диагностика показывает время последнего подключения/обрыва, число ошибок, последние события восстановления, статус Scheduler и EventBus даже если Discord Gateway в данный момент недоступен.
- В `Database` появились агрегированные метрики запросов: количество, медленные (от 500 мс), ошибки, последние/максимальные задержки. Значения SQL и параметры не логируются.
- `health.json` дополнен ключами Gateway, Discord HTTP, SQLite-query metrics и Backup Worker; поля `ready`, `discord`, `sqlite`, `scheduler`, `event_bus` сохранены.

### Автоматическое резервное копирование

- `BackupWorker` создаёт консистентные снимки SQLite через Online Backup API при старте и далее по расписанию.
- Каждый снимок проходит **проверку восстановления** во временный SQLite-файл с `PRAGMA quick_check`, `foreign_key_check` и проверкой `alembic_version`.
- Ротация очищает **только** `newsqad-auto-*.db`, не затрагивая ручные копии или `before-restore-*.db`.
- По умолчанию интервалы: 24 ч и 7 последних автоматических копий. Копии сохраняются внутри volume, а дополнительный экспорт направлен в подключаемый host-directory `./backups`.
- Ошибка создания/экспорта копии отображается в диагностике; бот не выключается из-за ошибки бэкапа.

### Проверки

- Python-тесты для перезапуска Scheduler и повторного запуска задания с одним `job_key`, конкурентного рассмотрения заявок и захвата тикетов, ротации и restore-probe.
- Web security-тест перечисляет **реально зарегистрированные** mutating API-маршруты и проверяет блокировку без авторизации/CSRF.
- Playwright в настоящем Chromium проверяет Ctrl+K, навигацию, несохранённые настройки, мобильное меню и отсутствие зависания Obsidian. Для браузера используется локальный одноразовый SQLite-сервер без реального Discord.

### /ann

- Команда **`/ann вид [цвет]`**. Аргумент `канал` удалён.
- Сообщение создаётся **в том же обычном текстовом канале**, в котором вызвана команда. Публикация в ветке/личных сообщениях не поддерживается.
- Права проверяются при открытии формы и повторно перед реальной отправкой. Объявления, черновики и отложенная отправка продолжают использовать прежний механизм.

## Конфигурация и обновление

1. Снимите копию перед обновлением:
   ```powershell
   docker compose exec bot python -m app.ops.backup create
   ```
2. Создайте папку для экспортируемых снимков рядом с `compose.yaml`:
   ```powershell
   New-Item -ItemType Directory -Force backups
   ```
3. Под Linux убедитесь, что пользователь `bot` внутри контейнера может записывать в host-directory; при необходимости выполните:
   ```bash
   docker compose run --rm --no-deps --user root --entrypoint sh bot -c 'chown bot:bot /app/backup-export && chmod 700 /app/backup-export'
   ```
   На Windows с Docker Desktop проверьте разрешения общего каталога и реальную запись через ручной запуск `run-once`. Не выдавайте общий доступ к `backups`.
4. Обновите проект:
   ```powershell
   git pull origin main
   docker compose up -d --build --force-recreate
   docker compose ps
   docker compose logs --tail=200 bot
   ```
5. Проверьте резервную копию и экспорт:
   ```powershell
   docker compose exec bot python -m app.ops.automatic_backup run-once
   ```
   Команда должна вывести `Экспорт за пределы volume: True`. Если вывод `False` или ошибка — исправьте каталог/права, затем повторите.
6. В веб-панели откройте **Диагностика**. Проверьте SQLite, Scheduler, EventBus, Discord Gateway, записи журнала и последнюю проверенную копию.

Параметры `.env`: `BACKUP_INTERVAL_HOURS=24` (1–168), `BACKUP_KEEP=7` (1–60), `BACKUP_EXPORT_HOST_DIR=./backups`. В контейнере export задаётся `BACKUP_EXPORT_DIR=/app/backup-export`.

**Нельзя выполнять** `docker compose down -v`. SQLite находится в `newsqad_data`. Копия в `./backups` защищает от удаления Docker volume, но не от потери всего диска — при необходимости вывозите её на другое устройство/хранилище.

### Проверка реального восстановления

Выполните на существующей резервной копии:
```powershell
docker compose exec bot python -m app.ops.automatic_backup probe /app/backup-export/ИМЯ_КОПИИ.db
```

Probe **не изменяет работающую БД**, он создаёт временную копию и проверяет её. Для полного восстановления в production сначала остановите контейнер и используйте процедуру `app.ops.backup restore` из `docs/OPERATIONS.md`. Discord-операции (роли, сообщения) не откатываются при восстановлении SQLite.

## Ограничения и эксплуатация

- Тестовый Discord API не равен живому серверу: для production обязателен ручной staging-прогон.
- SQLite metrics и ошибки HTTP в текущей версии являются суммарными показателями с момента запуска; история событий Gateway хранится ограниченно в `operations.json`.
- При сбое внешнего Discord API возможен **at-least-once** повтор: handlers должны быть идемпотентны. Scheduler lease сам по себе не обеспечивает exactly-once для внешнего Discord.
- Нет транскриптов закрытых тикетов и хранения приватных сообщений в операционном журнале.
